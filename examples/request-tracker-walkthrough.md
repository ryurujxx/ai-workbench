# 가상 요청 관리 도구 흐름

작은 업무 도구의 질문·요구사항·계획·검증·보고를 연결하는 예시다. 앱과 코드는 구현하지 않았다. 모든 답변은 가상이며 실제 실행 결과는 없다.

## 1. 접근 확인·초기 조사·1차 질문

프로젝트 README·기존 파일을 먼저 확인한다고 가정한다. 참고 START는 읽을 수 있지만 실제 프로젝트 정본 위치는 아직 없다고 가정한다. 구현 담당이 접근 가능한 프로젝트 안 `work-notes/`를 제안하고, 기획 담당은 파일을 만들지 않고 인계 내용만 작성한다. 도구 목적이 없으면 1차 개방형 질문을 보낸다.

> 운영팀에서 이 도구로 먼저 해결하려는 업무와 성공한 결과를 알려주세요.

가상 답변: 제목·내용으로 요청을 받고 신규→진행→완료로 처리 상태를 추적한다. 삭제·로그인은 이번 범위에서 제외한다.

답변을 요구사항 초안에 반영한 뒤, 일반적인 요청 처리 업무의 가설로 담당자별 상태 변경 권한, 중복 요청, 필수 입력, 완료 후 수정, 감사 추적 가능성을 검토한다. 외부 조사는 하지 않았으므로 이 항목들은 검증된 산업 사실이 아니라 일반 지식에 따른 가설이다. 결과를 바꾸는 완료 후 역전이와 빈 제목만 2차 질문으로 좁힌다.

> 완료 요청을 신규로 되돌리는 동작은 허용하나요? 허용 또는 차단 모두 아니라면 실제 규칙을 알려주세요. 답에 따라 상태 전이와 검증을 바꾸겠습니다.

가상 답변: 완료 후 역전이는 차단하며, 빈 제목도 받지 않는다. 담당자별 권한과 중복 요청 정책은 업무자가 모른다고 가정한다. 이번 필수 범위에는 영향이 없어 미해소 불확실성·범위 제외로 남기고 AI가 정책을 만들지 않는다.

## 2. 기록 위치와 요구사항

프로젝트 지정이 없어서 `work-notes/`를 선택했다고 가정한다. 정본 `work-notes/STATUS.md`에 같은 폴더의 REQUIREMENTS·DECISIONS·VERIFICATION·MVP_REPORT 경로를 명시한다. 이 예시는 그 실제 파일을 만들지 않는다.

| ID | 상태 범주 | 근거 | 우선순위 | 규칙·완료 기준 | 검증 설계 |
|---|---|---|---|---|---|
| EX-R1 | 확정된 요구사항 | 가상 1차 답변 | P0 | 등록하면 신규 상태로 목록에 보임 | 제목·내용 등록 후 1건 증가 |
| EX-R2 | 업무자가 확인한 정책 | 가상 2차 답변 | P0 | 공백 제목 거부, 목록 불변 | 공백만 입력 후 오류 확인 |
| EX-R3 | 확정된 요구사항 | 가상 1차 답변 | P0 | 신규→진행→완료 허용 | 각 상태 변경 확인 |
| EX-R4 | 업무자가 확인한 정책 | 가상 2차 답변 | P0 | 완료→신규 차단 | 거부 후 완료 상태 유지 |
| EX-U1 | 미해소 불확실성 | 업무자 모름 | 범위 제외 | 담당자별 권한 규칙 미정 | 구현·검증 안 함 |

사용자는 상태 규칙·필수 범위를 결정한다. AI는 조사한 기존 구조 안에서 함수·파일 구성 같은 작은 구현 사항을 정한다.

## 3. 대안과 최소 계획

기본안은 기존 구조 재사용, 대안은 새 프레임워크 도입이다. 두 안 모두 기능 구현 가능성이 있지만 새 프레임워크는 설정·학습·회귀 위험이 크고 성능 실험은 하지 않았다. 목적을 충족하는 데 도입 근거가 없으므로 기본안을 가상으로 선택한다. 이는 성능 우위를 검증한 선택이 아니다.

1. 기존 실행·저장 방식을 확인한다.
2. 등록·조회 경로와 EX-R1~R2 검증을 만든다.
3. 상태 전이와 EX-R3~R4 검증을 만든다.
4. 필요한 실행·화면 확인을 하고 근거와 한계를 보고한다.

이 작업에는 추가 스킬이 필수라는 근거가 없어 기본 방식으로 시작한다. 구현은 하지 않았으므로 이 계획도 실행 기록이 아니다.

반대 관점 검토에서는 중복 등록, 동시 상태 변경, 완료 후 잘못된 복구 차단이 실제 운영 실패가 될 수 있다고 본다. 중복·동시는 현재 답변과 범위가 없어 EX-U1과 함께 후속 후보로 남기고, 완료 역전이 차단은 EX-R4 검증에 반영한다.

기획 인계 묶음은 위 문제·목표, EX-R1~R4 확정 범위, EX-U1 미해소 상태, 기존 구조 선택과 배제 이유, 검증 설계, 제안 정본 `work-notes/`를 포함한다. 구현 환경에서 참고 폴더에 접근할 수 없다면 START의 복사·전달용 핵심 지침과 이 묶음을 대화에 붙인다.

## 4. 오류·경계·실패의 설계

공백 제목이 저장되는 가상 오류라면 원 입력과 저장 경로를 확인하고 입력 정규화 누락 가설을 최소 실험으로 확인한다. 원인이 확인되면 수정 후 공백 입력과 정상 등록을 함께 재검증한다.

제목 길이의 상한은 미확인이다. 임의 수치를 확정하지 않고 업무 영향이 있을 때 질문한다. 웹 화면이 있으므로 HTTP 응답과 별도로 등록·상태 변경·오류 표시를 확인하도록 설계한다.

| ID | 실제 구현 | 실제 결과 | 판정 |
|---|---|---|---|
| EX-R1 | 미구현 | 실행 없음 | 미검증 |
| EX-R2 | 미구현 | 실행 없음 | 미검증 |
| EX-R3 | 미구현 | 실행 없음 | 미검증 |
| EX-R4 | 미구현 | 실행 없음 | 미검증 |

사람 확인이 필요한 경우 입력·버튼·기대 상태를 안내하고 결과 전까지 미검증으로 둔다. 사용자가 확인을 전달하면 사용자 수동 확인으로 구분한다. 이 예시에는 그런 확인도 없다.

## 5. 진행 중 근거 누적·가상 보고와 자기 설명

MVP_REPORT에는 문제·목표는 1차 답변, 상태 규칙은 EX-R1~R4, 대안 비교는 기존 구조 선택, 오류·테스트는 실행 없음이라는 근거를 단계별로 연결한다고 가정한다. 상세 내용을 다시 꾸며 쓰지 않고 REQUIREMENTS·DECISIONS·VERIFICATION의 ID를 가리킨다.

보고: EX-R1~EX-R4의 요구사항과 검증만 설계했고 모두 미구현·미검증이다. EX-U1은 미해소·범위 제외다. 삭제·로그인은 범위 밖이다. 실제 실행법·성능·영속성은 확인하지 않았다. 참고 START의 접근은 가정일 뿐 실제 환경에서 검증하지 않았다.

자기 설명 질문: 제목 입력이 어떤 규칙을 거쳐 출력되는가? 완료 역전이를 막는 근거는 무엇인가? 왜 새 프레임워크를 도입하지 않았는가? 무엇을 실행했고 무엇이 미확인인가?

답변을 받지 않았으므로 사용자 이해가 확인됐다고 쓰지 않는다. 실제 프로젝트에서는 [PROMPTS.md](../PROMPTS.md) 1~14의 필요한 단계만 선택한다.
