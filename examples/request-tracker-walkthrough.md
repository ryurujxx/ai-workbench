# 가상 시간제한 요청 관리 도구 흐름

세 Codex CLI 세션으로 작은 요청 관리 도구를 90분 안에 만든다고 가정한 문서 흐름 검증이다. 앱과 코드는 실제로 구현·실행·제출하지 않았다. 아래 시각·답변·결과는 모두 가상이며 실제 성능이나 통과 근거가 아니다.

## 1. 접근·시간·평가 초기화

세 터미널이 같은 프로젝트를 읽을 수 있고 구현 세션만 코드·정본 쓰기 권한이 있다고 가정한다. 구현 담당은 프로젝트 안 `work-notes/STATUS.md`를 정본으로 제안하고 `EX-S-001`을 만든다고 가정한다. 기획·테스트는 읽기 전용이며 세 대화는 자동 공유되지 않는다.

- 가상 환경 정책: 공개 자료 반입은 허용되지만 외부 반출은 제한, 로컬 Git commit만 사용, 원격 Push·외부 업로드·외부 API 전송은 미수행
- 가상 제한시간: 90분, 09:00~10:30
- 가상 예산: 기획 질문 20분, 구현 55분, 검증은 구현과 병행, 최종 통합·제출 15분 예약
- 필수 산출물: 실행 가능한 앱, 소스, 실행 안내, 결과 보고
- 공개 평가: EX-E1 필수 기능 50점, EX-E2 예외 처리 20점, EX-E3 실행·검증 30점
- 서술형: 기술 선택 이유와 오류 해결 과정을 설명
- 실제 확인 상태: 모두 가상, 실행·제출 미검증

현재 시각은 계속 감시한다고 가정하지 않고 요구사항 인계, 구현 완료, 테스트 결과, 10:15 제출 단계 진입 때 다시 확인하도록 계획한다.

## 2. 1차 질문과 첫 즉시 인계

기획 세션은 다음 1차 질문을 보낸다고 가정한다.

> 운영팀에서 가장 먼저 해결할 업무와 성공 결과는 무엇인가요?

가상 답변: 제목·내용으로 요청을 등록하고 목록에서 확인한다. 상태 변경 규칙은 아직 확인 중이다.

기획은 등록 기능이 상태 정책에 의존하지 않는다고 판단하고 전체 기획을 기다리지 않는다.

| ID·버전 | 필수/선택 | 근거 범주 | 진행 상태 | 의존성 | 규칙·검증 기준 | 평가 | 인계 |
|---|---|---|---|---|---|---|---|
| EX-R1 v1 | 필수 | 확정된 요구사항 | 확정 / 구현 가능 | 없음 | 등록 후 신규 요청 1건 표시 | EX-E1 | EX-H1·순서 1 |
| EX-R2 v1 | 필수 | 미해소 불확실성 | 미확정 | 빈 제목 정책 | 공백 처리 미정 | EX-E2 | 없음 |
| EX-R3 v1 | 필수 | 미해소 불확실성 | 미확정 | 상태 전이 정책 | 신규→진행→완료 규칙 미정 | EX-E1 | 없음 |

EX-H1에는 읽은 `EX-S-001`, EX-R1 v1, 완료 기준, 테스트 절차, 인터페이스와 재작업 위험이 낮다는 판단을 포함한다. 사용자가 EX-H1을 구현 터미널에 붙이고, 구현은 `EX-S-002`에서 EX-R1을 `구현 중`으로 바꾼다고 가정한다. 기획은 그동안 2차 질문과 도메인 예외 분석을 계속한다.

## 3. 구현→테스트 순차 인계와 병행 기획

구현은 기존 구조 재사용을 선택하고 새 프레임워크는 시간·회귀 위험 때문에 배제한다고 가정한다. 성능은 측정하지 않았으므로 우수하다고 기록하지 않는다. 최소 실행 명령과 데이터 저장 방식을 먼저 확인하도록 계획한다.

EX-R1 구현이 끝나면 상태를 `구현 완료/미검증`으로 바꾸고 대상 커밋과 함께 EX-T1 요청을 출력한다고 가정한다. 테스트 세션은 EX-R1 v1만 정상 등록·재실행 유지 여부로 검증하고 다음 패킷을 반환하도록 설계한다.

| T-ID | 요구사항·버전 | 대상 | 검증 | 실제 상태 |
|---|---|---|---|---|
| EX-T1 | EX-R1 v1 | 가상 커밋 A | 정상 등록·목록 증가·재실행 유지 | 실제 실행 없음, 미검증 |

구현 담당이 실제 통과 근거를 받기 전까지 EX-R1은 `구현 완료/미검증`이다. 이 예시는 실행하지 않았으므로 `검증 완료`로 바꾸지 않는다.

동시에 기획은 일반 요청 처리 업무의 가설로 빈 입력, 완료 역전이, 중복, 담당자 권한을 검토한다. 외부 조사는 하지 않았으므로 검증된 산업 사실이 아니다. 가상 2차 답변으로 빈 제목 거부와 신규→진행→완료만 허용됨을 받았다고 가정하고 EX-R2 v2와 EX-R3 v2를 EX-H2·EX-H3으로 즉시 인계한다. 담당자 권한은 이번 범위 밖 미해소 불확실성으로 남긴다.

## 4. 변경 영향·오류·상태 복구

EX-R3 v2 구현 뒤 업무자가 완료→신규 복구를 관리자에게만 허용한다고 새로 답했다고 가정한다. 기획은 EX-R3 v3을 발행하고 기존 v2 구현·검증이 무효화될 수 있음을 즉시 알린다. 구현은 영향받는 상태 전이 코드와 EX-T3만 `오류/차단됨`으로 되돌리고 EX-R1·EX-R2 작업은 유지한다.

공백 제목이 저장되는 가상 오류는 `EX-ERR1`로 재현 조건, 입력 정규화 누락 가설, 수정, 원 증상 재테스트를 VERIFICATION에 연결한다. 실제 실행하지 않았으므로 원인 확인이나 해결 완료로 표시하지 않는다.

서버 장애가 09:50에 발생했다고 가정하면 마지막 STATUS에는 다음 최소 복구 정보를 둔다.

- 상태 개정: EX-S-006, 가상 시각 09:50
- EX-R1 v1 구현 완료/미검증, EX-R2 v2 구현 중, EX-R3 v3 오류/차단됨
- 코드·정본 작성자: 구현 세션
- 마지막 성공 명령·커밋: 가상 값이며 실제 근거 없음
- 실행 서비스·재시작 방법: 조사 필요
- 남은 시간: 가상 40분, 10:15부터 최종 통합·제출
- 다음 한 행동: 최소 실행 복구 후 EX-R2 관련 검증

새 세션은 대화 기억이 아니라 이 STATUS와 실제 Git·파일·프로세스를 대조해 재개해야 한다.

## 5. 평가 추적·시간 부족·최종 제출

MVP_REPORT에는 작업 중 다음 연결을 누적한다고 가정한다.

| 평가 | 배점 | 요구사항 | 구현 | 검증 | 증거 상태 |
|---|---:|---|---|---|---|
| EX-E1 필수 기능 | 50 | EX-R1 v1, EX-R3 v3 | 가상 파일·커밋 | EX-T1, EX-T3 | 실제 없음 |
| EX-E2 예외 처리 | 20 | EX-R2 v2 | 가상 파일·커밋 | EX-T2, EX-ERR1 | 실제 없음 |
| EX-E3 실행·검증 | 30 | 실행·제출 체크 | 미실행 | 최소 실행·화면·필수 파일·제출 | 미검증 |

10:15에 시간이 부족하면 담당자 권한, 중복 방지, 표현 개선은 중단하고 최소 실행 복구, 필수 기능, 가장 위험한 예외, 필수 파일, 제출 확인에 집중한다. 공개 배점이 없는 항목이라면 위와 같은 수치를 임의로 만들지 않는다.

최종 제출 전에는 데이터 로딩, EX-R1~R3 최신 버전, API·화면, 필요 시 Docker, 실행 안내, 필수 파일명과 정책상 허용된 제출 위치를 확인한다. 이 가상 반출 제한 환경에서는 지정된 로컬 제출 폴더까지만 확인하고 원격 Push·외부 업로드는 수행하지 않는다. 실제 허용된 제출 응답이나 목록을 확인하지 못하면 `제출 성공`이 아니라 `미확인`으로 기록한다.

## 6. 이 예시로 확인한 문서 흐름

1. 기획 중에도 EX-R1을 즉시 인계할 수 있다.
2. H/T 패킷의 ID·버전·STATUS 개정·커밋으로 구현과 테스트가 안전하게 연결된다.
3. STATUS에서 미확정, 구현 중, 구현 완료/미검증, 오류/차단됨을 구분할 수 있다.
4. 평가·서술형 근거가 DECISIONS·VERIFICATION·MVP_REPORT에 발생 시점부터 연결된다.
5. 제출 예약 시각에 선택 기능을 중단하는 우선순위 전환이 가능하다.
6. STATUS 최소 복구 정보로 장애 이후 재개 절차를 제시할 수 있다.
7. 최종 실행·데이터·기능·화면·Docker·필수 파일·제출 검증 항목을 구분할 수 있다.

이 예시는 문서 구조 검증일 뿐 실제 앱·Docker·세 터미널·제출 성공을 검증하지 않았다.
