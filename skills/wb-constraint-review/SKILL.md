# 제약 모델·알고리즘 검토

## 사용 범위와 입력

- 사용: 용량·필수 배정·시간·비용 등 여러 조건이 충돌하거나, 알고리즘 선택이 결과와 시간 위험을 바꿀 때.
- 제외: 단순 조회·정렬, 이미 승인된 선택을 설명하는 일, 측정 근거 없이 복잡한 솔버를 도입하려는 일.
- 역할: 기획은 모델·대안과 H 승인 제안, 구현은 승인 모델의 기준 구현·실험, 테스트는 완료 대상의 제약·목적함수 T 검증.
- 입력: 요구 ID·버전, Q/H의 승인 근거, 입력 규모·단위·자원, 결과 형식, 남은 시간, 기존 기준 해법과 실제 결과(있을 때).

## 수행

1. [WORKFLOW의 제약 절차](../../WORKFLOW.md#상황별-선택-제약최적화와-알고리즘-결정)에 따라 결정 변수·가능한 값·단위, 승인된 Hard/Soft, 목적함수 계산식·방향을 연결한다. 미확정 조건은 질문으로 두고 임의 가중치나 Hard/Soft를 만들지 않는다.
2. 입력만으로 알 수 있는 충돌과 필요조건을 먼저 검사한다. 총용량이 충분해도 개별 시간·자원 제약으로 불가능할 수 있다. 필수 대상 누락·미배정 처리와 해 없음의 표시를 확인한다. 휴리스틱 실패와 불가능 증거를 구분한다.
3. 작은 입력에서 손으로 가능한 해 또는 비용이 허용되는 한정 탐색으로 모델을 확인한다. 한정 탐색도 크기·중단 조건을 먼저 정한다. 규칙의 경계값을 바꿨을 때 기대 판정과 모형이 일치하는지 본다.
4. 단순 기준 해법, 실용 개선안, 필요할 때 정밀 방법 중 의미 있는 후보만 비교한다. 입력 크기 변수와 시간/메모리 복잡도, 제약을 지키는 방법, 보장하지 못하는 품질, 동률 처리·재현성·구현 위험·기준 구현 복귀를 설명한다. 특정 라이브러리 설치를 전제하지 않는다.
5. 같은 입력에서 유효성·목적값·시간을 분리해 평가한다. 여러 목표는 승인된 우선순위/가중치로만 비교한다. 참 최적값·유효한 하한/상한이 없는 경우 개선 전후 차이를 최적성 격차로 부르지 않는다. 결과를 바꾸는 선택은 사용자 승인 후 H 버전과 영향을 연결한다.

## 산출물·권한·복귀

승인 제약/미확정 조건, 가능한 해 확인/불가능 근거/존재 미확인, 후보 비교·실제 선택 이유와 검증 기준을 반환한다. 기획은 Q/H로, 테스트는 T로 전달하고 구현 담당이 STUDY의 기획·기술 영역에 통합한다. 정책 변경은 기존 승인 절차를 유지한다.

[AGENTS](../../AGENTS.md)의 역할 권한을 따른다. 검토 역할은 원본을 고치거나 솔버를 설치하지 않는다. 시험 자료·실험 결과는 공개 워크벤치 밖의 허용된 실제 과제 위치에 둔다. 측정 못 한 규모·최적성은 미검증으로 쓴다.

복잡한 모델·도구가 시간이나 환경에 맞지 않으면 기존 Codex로 승인 제약을 만족하는 작은 기준 해법과 제약 검사부터 진행한다. 기준 해법도 필수 요구를 못 맞추면 완료로 처리하지 말고 차단과 선택지를 보고한다.
