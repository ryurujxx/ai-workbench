# 반복 오류 원인 추적

## 사용 범위와 입력

- 사용: 수정 뒤 같은 실패가 재발하거나 입력·환경에 따라 달라져 원인 설명이 불명확할 때.
- 제외: 원인과 수정이 명확한 단순 오기, 전체 코드 감사, 플랫폼·IDE·감독 연결 자체의 장애.
- 역할: 구현은 승인 범위의 진단·최소 수정, 테스트는 완료 대상의 재현·독립 확인 후 T 보고, 기획은 정책/입력 의미 충돌 분석과 Q/H 제안만 한다.
- 입력: 요구/H/T 버전, 실제 오류·발생 시점·재현 명령/입력, 기대 동작, 마지막 정상 상태, 시도한 변경과 관찰, 서버 소유권·남은 시간. Git 커밋이 없으면 파일 상태·확인 시점을 사용한다.

## 수행

1. [WORKFLOW의 장애 구분](../../WORKFLOW.md#8-시간제한세션-복구제출)부터 적용한다. 프로젝트 코드·서버 문제인지 확인한다. 플랫폼 자체 장애 근거가 있으면 공식 신고·제공 재연결 안내로 넘기고 관리 설정·프로세스를 조작하지 않는다.
2. 최소 실패 사례와 가능하면 같은 환경의 정상 사례를 대조한다. 재현되지 않으면 성공으로 결론 내리지 말고 입력·실행 순서·빈도·차이를 좁힌다. 동일한 실패 명령을 새 근거 없이 계속 반복하지 않는다.
3. 입력 → 파싱/변환 → 계산 → 저장/응답 경계 중 처음 값이 달라지는 곳을 찾는다. 기존 로그·상태부터 읽는다. 추가 계측은 구현 담당이 허용된 범위에서 최소로 하고 비밀값·전체 데이터·환경 변수 일괄 출력을 피한다.
4. 가장 구별 가능한 가설 하나와 예상 관찰을 정하고 작은 실험을 한다. 관찰이 지지/반박/판단 불가 중 무엇인지 기록한다. 여러 수정·의존성 갱신을 한꺼번에 하지 말고 실패한 변경은 다른 작업을 보존해 되돌린다. 원인을 확정할 근거가 부족하면 가설로 남긴다.
5. 구현 담당이 원인에 맞는 최소 수정을 하고 원 실패 사례·관련 회귀·실행 흐름을 확인한다. 정책이나 기술 구조 변경이 필요하면 영향과 재승인을 H에 연결한다. 근거가 늘지 않거나 제출 여유를 침해하면 시도를 멈추고 검증된 정상 상태·차단·다음 판단을 보고한다. 고정 재시도 횟수를 강제하지 않는다.

## 산출물·권한·복귀

재현 입력·기대/실제 → 가설/판별 실험·관찰 → 원인 또는 미확인 → 수정·재검증을 반환한다. 테스트는 T로, 기획은 Q/H로 제안하고 구현만 STATUS의 상태·복구 정보와 STUDY의 오류 근거를 갱신한다. 긴 진단 보고서를 별도로 만들지 않는다.

[AGENTS](../../AGENTS.md)의 파일·서버·포트·데이터 소유권을 유지한다. 읽기 권한만 있는 역할은 진단 스크립트·설정을 원본에 쓰지 않는다. 공개 Skill 폴더에 실제 로그를 저장하지 않으며 직접 관찰하지 못한 원인·해결은 미검증으로 표시한다.

이 절차가 과하면 기존 Codex의 오류 메시지 확인 → 승인 범위의 최소 수정 → 해당 사례 재실행으로 돌아간다. 미해결 항목만 차단하고 독립 기능·필수 제출 준비는 계속한다.
