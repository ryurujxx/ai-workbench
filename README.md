# AI 개발 워크벤치

기획·구현 A·독립 테스트의 기본 3세션으로 **초기 MVP 우선 → 병렬 기획 → 첫 통합 테스트 → 상세 기능 개선**을 이어 간다. 입력→실제 핵심 처리→저장/조회→필요한 API·웹→사용자 확인의 최소 전체 흐름부터 연결하며 불필요한 기술 형태는 강제하지 않는다. [구현 B](EXAM_QUICK_GUIDE.md#선택형-구현-b)는 사용자가 원할 때만 추가한다.

사용자는 [시험 중 빠른 안내](EXAM_QUICK_GUIDE.md)와 [START 복붙 프롬프트](START.md)부터 읽으면 된다. 실제 과제 루트에 준비된 ai-workbench/를 참고하되 그 README를 과제 지시서로 혼동하지 않는다.

## 처음부터 제출까지

1. 터미널 1에서 [START 00](START.md#step-00--과제-이해mvp-초안)으로 기획 역할을 처음 시작하고 과제·데이터·기능별 쉬운 설명과 PROJECT MVP 초안을 본다. 응답이 끝나면 읽으면서 **같은 세션에 [01](START.md#step-01--업무-분석1차-질문독립-기획-후보)**을 보내 업무 분석·미확정 정책·1차 질문과 최소 전체 MVP 계약을 신속히 정리한다. 명시된 필수 요구·필수 제약을 빠뜨리지 않고 초기/후속/차단을 나눈다.
2. 초기 MVP의 중요한 선택만 명시적으로 승인하고 05/15로 전체 흐름의 경량 H 하나 또는 연결 H 묶음을 발행한다. 필요한 기능만 [17](START.md#step-17--mvp-기능별-가벼운-기획-협의)로 동작·기본안·선택을 가볍게 합의한다. 심층 비교 04는 필요한 기능만 사용하고 이미 승인된 독립 기능을 기다리게 하지 않는다. qa의 이번 질문만 업무자에게 보내고 답변은 기본적으로 우측 업무자 채팅 원문 전체를 03에 붙이기만 한다(A 직접 기록도 유지). 기획은 원문 보존·발화자/Q 연결·중복/모호함을 수신 계약으로 대조하고 중요한 정책/기술은 사용자 승인 후 05 또는 자유 회의 15로 H 전문을 발행한다.
3. 첫 H는 터미널 2 START 06, 추가 H는 07로 전달한다. 구현 A는 H 전문을 읽고 실제 핵심 흐름부터 구현·자체 검증·사용자 카드·T 요청을 기록한다. 그동안 기획은 17/04로 상세안을 병렬 협의하며 후속 H는 안정적인 인계 시점에 적용한다.
4. 전체 서비스/H 완료 전이라도 첫 검증 가능한 흐름의 요청이 나오면 터미널 3 START 08, 후속은 같은 세션 14로 독립 검증한다. 결과는 구현 담당 09로 반환한다. 하위 T 통과를 전체 MVP 통과로 표시하지 않는다.
5. 상태 전이 직후 기획·A·테스트가 자기 원천과 잠금 아래 PROJECT/HANDOFF를 자동 갱신한다. B의 기록은 A가 확인 후 반영한다. 수동 재조회는 16, 재개 11, 핵심 학습 10, 제출 전 실제 환경 점검은 12다.
6. 사용자 최종 확정 후 AI 작업은 종료하며 AI 금지 후속 문제는 사용자가 직접 답한다.

질문 발굴/기록은 01·17·04·15·H 작성 등 모든 기획 활동의 기본 의무다. 기존 답/중복을 확인하고 AI 자체조사와 업무자 판단을 나눠 필요한 Q를 qa에 기록한다. STEP 02는 누적 질문의 전달 문구·이번 묶음 복사에만 쓰는 선택 메뉴이며 실제 전달 확인과는 다르다. 새 질문/근거/상태 변화가 없으면 불필요하게 저장하지 않는다.

기획은 [공통 문제 해결 절차](WORKFLOW.md#기능-기획의-공통-문제-해결-절차)로 문제/사용자 결과·제약/목표·입력 가능성·해결 전략·트레이드오프를 필요한 깊이만 검토한다. 17은 가벼운 협의, 04는 중요한 복잡한 선택의 선택형 심층 비교다. 단순 기능에 대안/질문/실험을 강제하지 않으며 승인 설계는 PROJECT/H, 실제 구현 근거는 구현 담당의 STUDY로 연결한다.

이 구조는 권장값이다. 실제 과제의 생성/위치 제한·기존 동등 문서가 우선이며 필요한 시점에만 만든다. 구 qa/STATUS에 있는 H/T 전문도 실제 ID·버전·경로로 호환하고 안전한 이관 전에는 원문을 제거하지 않는다.

기본 역할 선언은 최초 00/06/08만(선택형 B는 빠른 안내의 별도 초기 프롬프트), 후속 STEP은 기존 역할·권한을 유지한다. 초기화/잘못된 세션이면 11에서 실제 파일과 역할 근거를 대조하고 쓰기 전에 복원한다.

세션 대화는 공유되지 않는다. 사용자는 H/T **전문 또는 ID·버전·실제 전문 경로**를 전달한다. 상대는 전문을 직접 읽고 미접근이면 전문을 요청한다. 제목·줄 번호·대상 JSON만으로 구현/검증/결과 반영하지 않는다.

PROJECT 기획 원천은 기획만, 코드의 기본 소유·STATUS·STUDY·요청은 구현 A만(B는 명시적 코드 위임·반환 예외), 결과는 테스트만 쓴다. PROJECT 집계와 HANDOFF는 [CreateNew 원자적 파일 잠금으로 직렬화](WORKFLOW.md#공통-mvp-현황과-문서-동기화)한다. 서로 다른 열을 동시에 편집하지 않는다. 상태 변경 때 저장하고 다음 세션 작업 시작 때 실제 읽으며 **백그라운드 감시·자동 알림·새 서비스 설치는 없다**.

핵심 기능 없이 기반 화면/데이터만 있으면 최소 MVP 미완성이다. 초기 MVP 밖의 후속 필수도 과제 전체 완료 전에 남은 요구로 추적하며 근거 없는 퍼센트는 쓰지 않는다. MVP의 기획·구현·독립 T는 별도 단계다. 사용자 수동 확인·제출 검증은 상세로 분리한다. 필수 하위 C-03.1이 미완료이면 상위 C-03도 전체 완료가 아니다. H 발행≠실제 수신, 결과 파일 작성≠구현 반영이며 누락/충돌/대상 불일치는 미확인이다.

## 선택형 Skill 빠른 선택

일반 작업은 기존 WORKFLOW로 충분하다. 아래는 반복되는 전문 점검을 필요할 때만 읽는 라이브러리이며 **다섯 개 모두 설치 없이 파일로 읽을 수 있다**. 첫 H·첫 실행을 기다리게 하지 않는다. 필요 없으면 건너뛴다. 새 도입 판단은 [START STEP 13](START.md#step-13--skillmcp도구-필요성-판단-및-선택)을 사용한다.

| 문제 → Skill | 요청할 담당 | 필요한 입력 | 쓰지 않는 편이 좋은 경우 |
|---|---|---|---|
| CSV 스키마·결측·조인 → [wb-data-check](skills/wb-data-check/SKILL.md) | 기획 조사 / 구현 처리 / 테스트 검증 | 파일·필드·Q/H 정책·허용 범위 | 헤더 확인만으로 충분함 |
| 제약·목표 충돌 → [wb-constraint-review](skills/wb-constraint-review/SKILL.md) | 기획 비교 / 구현 실험 / 테스트 검증 | 승인 제약·목적함수·규모·기준 해법 | 단순 조회·정렬 |
| 정답 근거 부족 → [wb-independent-check](skills/wb-independent-check/SKILL.md) | 테스트 우선 / 구현 자체 검산 / 기획 기준 | Q/H·원본·결과·대상 버전 | 빌드·UI 모양만 확인함 |
| 원인 불명·재발 → [wb-debug-trace](skills/wb-debug-trace/SKILL.md) | 구현 우선 / 테스트 재현 / 기획 정책 분석 | 실제 오류·재현·마지막 정상 상태 | 단순 오기·플랫폼 자체 장애 |
| 큰 입력의 시간·메모리 → [wb-performance-check](skills/wb-performance-check/SKILL.md) | 구현 측정 / 테스트 검증 / 기획 기준 | 기준/후보·입력 규모·환경·남은 시간 | 병목이 없거나 제출 직전 |

Clone 위치인 `ai-workbench/skills/`를 유지한다. 실제 과제의 `.agents/skills`·AGENTS·설정을 자동 생성·덮어쓰기하지 않는다. 공식 Codex는 작업 위치에서 저장소 루트까지의 `.agents/skills`를 탐색하지만 이 하위 참고 폴더의 `skills/`는 그 등록 경로로 배포하지 않는다. **직접 열람은 자동 등록·선택 목록 표시의 증거가 아니다.** Cofa IDE의 자동 인식·하위 에이전트 호환성은 미검증이다. [공식 Skill 안내](https://learn.chatgpt.com/docs/build-skills)

현재 역할의 세션에 다음처럼 요청한다. 경로의 `ai-workbench/`는 실제 Clone 폴더 이름에 맞춘다.

```text
테스트 후속: ai-workbench/skills/wb-independent-check/SKILL.md를 읽어.
승인된 T 요청 [T 요청]의 결과를 원본 수정 없이 독립 검산해줘.
직접 열람으로 적용하고 설치·등록·설정 변경은 하지 마. 기대값 근거와 미검증을 T로 반환해.
```

이처럼 구체적으로 요청한 범위는 사용 승인으로 본다. 처음 도입을 제안할 때만 STEP 13에서 비교·승인을 받는다. 기획·테스트도 승인된 지침을 자기 역할의 읽기·분석·검증에 적용할 수 있지만 환경 적용·설치·설정 변경은 구현 담당만 승인과 환경 허용을 확인해 수행한다.

등록을 별도로 승인·허용받고 목록에서 실제 인식을 확인한 경우에만 `$wb-independent-check` 같은 호출을 사용할 수 있다. 목록에 없으면 위 직접 읽기로 돌아간다. 이 라이브러리는 전역 설정·MCP·패키지 설치·등록 스크립트를 요구하지 않는다. 다른 위치로 옮겨 쓰면 공통 문서 링크도 실제 `ai-workbench/` 경로로 확인해야 한다.

실패·시간 부족이면 새 설치를 멈추고 기존 Codex·프로젝트 도구와 WORKFLOW의 작은 실행·검증으로 복귀한다. 변경은 구현 담당이 자기 변경만 안전하게 되돌리고, 미검증·복구 상태와 중요한 근거만 기존 H/T·STATUS·STUDY에 연결한다. 실제 과제 입력·로그·결과는 공개 `ai-workbench/skills/`에 저장하지 않는다.

templates/는 공개 재사용 양식만 보관한다. 실제 프로젝트 문서에 복사할 때 링크는 실제 경로로 조정한다.

실제 비공개 자료·데이터·로그·화면·결과물은 이 공개 저장소에 포함하거나 허용되지 않은 외부 서비스로 보내지 않는다. 공개 자료 Clone 허용은 프로젝트 결과물의 외부 반출 허용을 뜻하지 않는다. 일반 개발 환경에서 사용자가 승인한 작업 브랜치 Push·PR은 해당 환경 정책에 따라 사용할 수 있다.

`ai-workbench/`가 작업공간 안에 있다는 이유만으로 자동 삭제·은폐하거나 제출 구조를 바꾸지 않는다. 실제 과제의 제출 범위와 명시적 파일 조건을 먼저 따른다.

실제 업무자 질문·답변은 공개 `ai-workbench/templates/`가 아니라 실제 과제 최상위 작업공간의 `templates/qa.md`에 둔다. 비공개 Q&A를 공개 저장소에 Commit·Push하지 않는다.
